# Ontology Authoring: Point of View and Architecture

**Status (2026-10-06):** proposal. Nothing here is built. Tasks are in [ontology-burndown.md](ontology-burndown.md) under "Side quest: ontology authoring" (OA-0 to OA-10).

## Recommendation in brief

- Build ontology authoring **inside Helios**: a library in `shared/helios_core/ontology/`, a router in the existing Helios API, one Workbench Job for long LLM work, and a workbench on the Ontology page. Do not create a new application.
- The user never writes LinkML. They work on a **draft**, which is a list of small, reviewable changes on top of a shipped base (core, or core plus a domain pack). Helios compiles the draft to LinkML and publishes it through the path that exists today.
- The LLM **proposes and explains; it never publishes**. Every suggestion carries the evidence it came from and waits for a person to accept, edit or reject it, the same way discovery proposals do.
- A draft can be **tried before it is activated**: a trial crawl on a sample, scored with the existing harness.

## Where we are today

- The ontology is three hand-written LinkML files in the repository (`core`, the `retail` pack, an example tenant extension) plus a hand-written warehouse mapping. Publishing reads a file path under `ontology/`.
- One version (0.2.0) is published and active. The header of the tenant extension says it is "generated by `propose_ontology`"; that generator does not exist.
- An end user therefore cannot create or change an ontology without editing YAML in the repository and knowing LinkML.

What already exists and should be reused:

| Piece | Where | Reuse |
|---|---|---|
| Parse, check, publish, activate, immutable versions | `helios_core/ontology/parser.py`, `console/ontology.py`, `helios_index.ontology_versions` | Unchanged; drafts feed it |
| Proposal then human review | `helios_core/propose`, `helios_core/review.py`, the review UI | The interaction pattern and UI components |
| LLM client, provider settings, token reporting | `helios_core/llm` | All model calls |
| Grounded LLM extraction with a reply cache | `apps/helios/crawler/llm_arm.py` | Evidence gathering, caching, provenance |
| Tool-calling assistant loop with traces | `console/assistant.py` | The authoring copilot |
| Crawl index and scoring harness | `helios_index.*`, `crawler/evaluate.py` | Evidence for proposals; measuring a draft |
| Job launch from the API | `console/crawl_jobs.py` | The proposal Job and trial crawls |
| Permissions and audit | `authz` (`ontology.read`, `ontology.edit`), `audit` | As is |

## Who the user is

A domain expert or data steward. They know the business ("a franchise partner is not a customer") and can judge a suggestion. They do not know LinkML, graph modelling or the warehouse's key columns. The tools must let them **recognise and correct**, not author from a blank page.

## The tools a user needs

Ordered by the work a user actually does.

### 1. A starting point

- Choose a base: core only, or core plus a domain pack. Never an empty page.
- See the base read-only, with what it already covers, so the user adds only what is missing.

### 2. Suggestions from evidence

The LLM proposes additions, each with a reason and the evidence behind it:

- **From the semantic model:** datasets, fields, relationships and glossary terms that have no class ("`store_returns.sr_reason_sk` joins to `reason`: propose class Reason").
- **From crawled documents:** things mentioned often that nothing in the ontology covers (unlinked mentions, repeated noun phrases, labels in PDFs), and statements that look like a new kind of claim.
- **From a description in the user's own words:** "we also track warranty claims and repair visits".

A suggestion is one of: a class under a named parent, an attribute, a relationship, a claim type with its subject and object, a warehouse mapping, or a set of cue phrases.

### 3. Review

- A queue of suggestions with accept, edit and reject, in bulk and one at a time. This is the discovery review screen applied to ontology changes.
- Each suggestion shows its evidence: the table and sample values, or the passages.

### 4. A structured editor

- Forms, not YAML: name, parent, definition, attributes, relationships.
- Small LLM helpers on demand: write a definition, suggest the parent, find near-duplicates and synonyms, point out a class that is really an attribute.
- The graph view that exists today, showing the draft's additions in a distinct style.

### 5. Warehouse mapping

- For each class: which dataset it lives in, and which columns are its key, business key, display name and aliases.
- The LLM suggests the mapping; Helios **checks it against real data** (is the key unique, how many rows, are names repeated) and shows samples.
- This is the part users cannot do unaided, and the part the crawler's accuracy depends on most.

### 6. Claim vocabulary and cues

- Define a claim type: its meaning, what it is about and what it points to.
- The LLM suggests cue phrases from sample passages; the user sees which passages each cue would match before accepting.
- Cues live in the crawler settings, so this tool writes a new settings version alongside the ontology draft.

### 7. Validation

Run continuously, and required before publish:

- **Structure:** leaves only, nothing imported is redefined, no cycles, names valid and unique, every class has a definition.
- **Mapping:** every mapped table and column exists in the published semantic model (the check that exists today); every class a document can mention has identifiers.
- **Coverage questions:** the user writes a few plain questions the ontology should support ("which stores have the most damaged-package returns?"); Helios reports which classes and relationships each needs and what is missing.

### 8. Trial and impact

- **Difference** from the active version: classes, attributes, mappings and claim types added.
- **Trial crawl:** run the crawler on a sample with the draft, without activating it. Show what would be found that is not found today, and the scores where ground truth exists.
- **Impact warning:** activating a version changes what every later crawl looks for.

### 9. Lifecycle

- Draft, validate, publish as an immutable version, activate, with history, difference between versions, and return to an earlier version.
- Who changed what, and which suggestions came from the model (with provider, model and prompt version).

### 10. A copilot

A chat panel on the workbench that can use all of the above: "add a class for warranty claims under Claim, map it to the `warranty` table, and show me what a crawl would find". Its changes land in the draft as suggestions to review. It cannot publish or activate.

## Architecture

### The central change: drafts instead of files

Today a published ontology is whatever a repository file says. For end users, the unit of work becomes a **draft**:

- **Base:** a shipped schema and version (core, or a pack). Shipped files stay read-only in the repository.
- **Changes:** an ordered list of small operations, each with its author (a person or the model), reason, evidence and decision.
- **Compile:** base plus accepted changes produces a LinkML extension file and a mapping file, deterministically. The same draft always compiles to the same bytes.
- **Publish:** the compiled files go through the existing parse, check and publish path. Nothing downstream changes: the crawler, the graph and the page still read published versions.

The operations are a closed set, which is what makes LLM output safe to accept:

`add_class`, `set_description`, `add_attribute`, `add_relationship`, `add_claim_predicate`, `add_enum_value`, `map_class`, `set_identifiers`, `add_alias`, `add_cues`, and `remove_*` for anything the draft itself added.

A draft can only add leaves. There is no operation that edits the base, so the "layers only add leaves" rule is enforced by construction.

### Components

```
Browser: Ontology page, new "Drafts" workbench
   │
   ▼
Helios API ── /api/v1/ontology/drafts/...        (new router, in the existing API)
   │            permissions: ontology.edit; every call audited
   ├── helios_core/ontology/authoring/    draft model, operations, compiler, validators, diff
   ├── helios_core/ontology/suggest/      evidence gatherers, prompts, grounding, reply cache
   ├── metadata store                     drafts, changes, suggestion runs   (new migration)
   ├── artifact store                     compiled LinkML and mapping per draft revision
   ├── helios_index (lakehouse)           published versions (as today); crawl evidence (read)
   ├── helios_core.llm                    short assists, inside the request
   └── Workbench Jobs
         helios-ontology-suggest          long suggestion runs over the model and documents
         helios-crawl                     trial crawl with a draft's compiled version
```

### API

All under `/api/v1/ontology`, next to the existing endpoints.

| Endpoint | Purpose |
|---|---|
| `GET /bases` | Shipped schemas a draft can start from |
| `POST /drafts`, `GET /drafts`, `GET /drafts/{id}`, `DELETE /drafts/{id}` | Create from a base, list, read (with the compiled graph), discard |
| `POST /drafts/{id}/changes` | Add one or more operations by hand |
| `POST /drafts/{id}/changes/{change}:decide` | Accept, edit or reject; bulk variant |
| `POST /drafts/{id}:suggest` | Start a suggestion run (source: model, documents or a description); returns a run |
| `GET /drafts/{id}/suggestions/{run}` | Progress and results of a run |
| `POST /drafts/{id}:assist` | A short helper: define, suggest parent, find duplicates |
| `POST /drafts/{id}/mappings:probe` | Check a proposed mapping against the warehouse and return samples |
| `POST /drafts/{id}:validate` | Structure, mapping and coverage results |
| `GET /drafts/{id}/diff` | Against the active or a named version |
| `POST /drafts/{id}:trial` | Start a trial crawl on a sample; returns a crawl run |
| `POST /drafts/{id}:publish` | Compile, then the existing publish; refuses if validation fails |
| `POST /drafts/{id}/copilot/turn` | One turn of the copilot |

The existing `:check`, `:publish` (from a file path), `:activate`, `/versions` and graph endpoints stay as they are.

### How the LLM is used

- **Model:** the project default, with the session override for interactive calls. A Job can only use the project default, as with the LLM crawler.
- **Three kinds of call:**
  - *Short assists* in the request path, bounded by the existing 30-second limit.
  - *Suggestion runs* in a Job: many calls over the semantic model and document samples, with the reply cache and token totals used by the LLM crawler.
  - *Copilot turns*: the assistant's tool loop, with tools that call the same functions as the API.
- **Output is always operations**, validated against the closed set. Anything else is discarded and counted.
- **Grounding:** a suggestion from documents must quote passages that exist; one from the warehouse must name tables and columns that exist. Ungrounded suggestions are dropped, as the LLM crawler drops quotes that are not in the document.
- **Provenance:** provider, model, prompt version and hash on every suggestion run. No keys stored.
- **The model sees** the base ontology, the semantic model's structure, sampled values and sampled passages. It does not see ground truth or golden questions.

### Data access

- Warehouse probes and samples run as the signed-in user through the existing delegation, so Ranger decides what they can see.
- Document evidence comes from the crawl index. Document text is not filtered per user today (crawler item DS-7); the same limit applies here and should be closed before real documents are used.

### Changes outside the new code

- **Crawler:** accept an explicit ontology version, so a trial crawl can use a published-but-inactive version. Today it always takes the active one.
- **Publish:** accept compiled content from the artifact store as well as a repository path.
- **Search and browsing:** trial crawls must not feed them. Treat a trial as a non-serving run, as LLM crawls are.

## One application, or its own?

**Recommendation: integrate into the Helios API.** Keep it a separate package and router so it can be moved later.

| | Integrated (recommended) | Separate application |
|---|---|---|
| Sign-in, permissions, audit | Already there | A new delegation scheme, as the MCP server needed |
| Publish path, metadata store, LLM settings, crawl index | Direct calls | Called over HTTP, or duplicated |
| Operations | Nothing new to deploy | Another Workbench Application: resources, URL, CORS, secrets, health |
| Load | Light and occasional; long work goes to a Job | Isolated, but there is little to isolate |
| Risk to the API | Slow model calls in requests | None |
| Independent release | No | Yes |

Reasons:

- Authoring is the front half of something Helios already does (check, publish, activate). Splitting it would put a network boundary through the middle of one workflow.
- The MCP server and the graph gateway are separate applications because each is a different kind of server (a protocol endpoint, a database). Authoring is ordinary API work.
- The one real risk, slow model calls tying up the API, is handled by sending suggestion runs and trial crawls to Jobs and keeping in-request assists short.

When to revisit: if authoring is offered to people who do not use the rest of Helios, or if suggestion load grows enough to need its own scaling.

## Risks and open questions

1. **Suggestion quality is unknown.** Nothing here has been tried. The first task is a spike that measures it on the retail corpus by hiding the retail pack and seeing how much of it the model recovers.
2. **Mappings are the hard part.** A plausible class with a wrong key column silently damages resolution. Probing real data and the trial crawl are the safeguards; they need to be good.
3. **Who may publish and activate?** Today one permission, `ontology.edit`, covers both. Authoring by more people may need "propose" separated from "publish".
4. **One ontology or one per organization?** There is a single active version today. Drafts are designed per organization; whether activation becomes per organization is a product decision.
5. **Cost.** Suggestion runs over documents use the model heavily. Token totals are recorded; prices are unset.
6. **Changing or removing published classes** is out of scope for the first version. A new version can add; migration of existing crawl results is not designed.
