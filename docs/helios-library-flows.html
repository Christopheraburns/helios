Helios decomposition · target design

How the four Helios libraries work together

A typical deployment does two things. First it builds a semantic model of a warehouse and publishes it. Then agents use that model to answer questions with SQL that runs as the person asking. Each row in the diagrams below is one library, so you can see which library does which step.

1 · Build and publish a semantic model

This runs offline from the helios command or a scheduled job. Only helios-model and helios-core take part. Plugins reach the catalog, the warehouse, the LLM and storage.

2 · Answer a question

This runs whenever an agent calls a tool. helios-model is not involved. helios-serve reads the published model, and the warehouse checks access using the caller's own identity.

Numbered step, in order Supporting call into a plugin, the kernel or an outside system

The four libraries

helios-core

The kernel. It holds settings, the plugin loader, the model registry and artifact store, the semantic compiler, and the Caller type.

Depends on
nothing in Helios
Key API
Settings, plugins, Caller
Phases
1–4

helios-model

Builds models. It harvests and profiles a source, has an LLM propose the semantics, and publishes the version a person approves.

Depends on
helios-core
Key API
harvest, profile, propose, publish
Phase
5

helios-serve

Uses models. It provides seven tools as plain Python functions with a registry, plus the Helios facade for application code. It has no MCP dependency.

Depends on
helios-core
Key API
run_query, tool registry, Helios
Phase
6

helios-mcp

A local stdio MCP adapter. It serves the helios-serve registry to one developer's agent, without HTTP or authentication.

Depends on
helios-serve, MCP SDK
Key API
helios mcp
Phase
7

helios-cloudera is an optional plugin package. It adds the Impala engine, the Atlas catalog, Cloudera AI Inference defaults and the Workbench settings profile.

Daedalus serves the same tool registry over MCP for shared deployments. It verifies each caller and passes it to helios-serve as a Caller.

Your host app pip-installs the libraries and owns deployment, configuration and identity. It can also call the Helios facade directly instead of going through MCP.

Status: this is the design after burndown Phase 7. Today only helios-core is a package in packages/. The model-building, tool and MCP code still lives in apps/helios and moves out in Phases 5–7.
